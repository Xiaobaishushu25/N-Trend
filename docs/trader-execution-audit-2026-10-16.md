## 代码检查

1. `register_condition` 和 `on_price_update` 在运行路径中没有调用方，调用仅出现在执行引擎单元测试。服务端扫描产生通知、实时行情触发通知，没有将这些事件注册并推进到执行引擎。因此切换 FullAuto 不会自行接通自动报单链路。
2. 全自动开仓与人工确认开仓均在桥接返回 `success=true` 时建立策略持仓；Python 的成功仅代表 `ReqOrderInsert` 同步返回 0，不代表柜台接受，更不代表成交。
3. 执行引擎没有消费委托、成交回报来推进成交数量、实际均价、拒单和撤单状态。
4. 平仓仅 FullAuto 分支提交订单，且忽略提交结果；随后无条件标记 `is_closed=true`、清零策略数量并记入历史。SemiAuto 的注释声称成交后自动平仓，但实现不会向柜台发送平仓单。
5. 止损使用止损价作为普通限价单价格，Python 设置当日有效、立即提交、`StopPrice=0`。没有未成交追踪、撤单确认、改价重报及剩余手数管理。
6. 同一条件单的 Pending 状态只触发一次；但注册函数按 UUID 新建条件单，没有对 event_id 去重。拒单或 HTTP 错误后全自动条件单还可能停在 Triggered，没有明确恢复流程。
7. 条件单、策略持仓、成交历史和当日亏损计数均主要位于内存；目前只有执行配置持久化。重启后缺少挂单和托管仓位恢复链路。
8. 通知路径以 `latest > entry` / `latest < entry` 判断突破；执行引擎以 `high >= entry` / `low <= entry` 判断触及，语义并不相同。行情轮询也不能保证捕获采样间隔内所有瞬时触价。

## 条件单的区别

SimNow 官方终端下载页介绍了“快期APP-上期技术云条件单版本”，提供价格触发等云条件单能力：
https://www.simnow.com.cn/static/softwareDownload.action

这不等于当前普通 CTP 报单代码已接入云条件单，也不能仅凭 API 存在触发条件字段就确认指定环境支持。当前条件单只在自有执行引擎内存中，尚未上传给云条件单服务。条件触发与成交是两个阶段；条件单也不保证触发价成交。

## 建议修复顺序

1. 将预警注册、实际合约行情和交易回报接入执行引擎；避免用主连价格代替实际交易合约触发与报单。
2. 明确提交中、委托中、部分成交、已成交、撤单中、已撤单、拒单、状态待核实等状态；成交回报驱动持仓和流水。
3. 按预警事件、账户和交易日建立持久化唯一约束，固定委托标识，网络超时先核对委托再重试。
4. 实现止损后的未成交订单管理：根据盘口和允许滑点选择价格，处理部分成交，撤单确认后才对剩余数量重报；没有对手盘时保留风险敞口并告警。
5. 实现重启恢复、断线补偿及半自动持仓的平仓规则，再进行 SimNow 端到端验收。

在这些问题修复并验收之前，当前 FullAuto 设置不能作为无人值守交易能力已具备的依据。
