## CTP 查询的锁顺序问题

`perf` 以49Hz采样十秒，采集903个样本、没有丢样。56.04%的总采样落在 `pthread_spin_lock`，调用链包括 `CThostFtdcUserApiImpl::ReqQryOrder` → SWIG查询包装层。

旧 `_query_loop()` 在持有 Python 状态锁时调用 CTP SDK。回报处理也要获取这把锁；若 SDK 正在等待回报线程，便可能形成锁顺序反转。查询一直占用状态锁还会让 `/health` 和 `/snapshot` 无法响应，后端继而把柜台连接标为中断。

只读反汇编确认服务器安装的查询包装层包含 `SWIG_Python_Thread_Allow`，原生调用释放 GIL；仅靠 GIL 不能避免上述状态锁冲突。

修复内容：

- 在状态锁内预留唯一查询槽位，离开状态锁后调用 SDK；发送失败时再加锁恢复状态。
- 报单使用独立提交锁维持幂等性，日志仍先于真实报单落盘，SDK调用不持有SPI回报需要的状态锁。
- 紧急撤单、平仓接口先复制待处理列表，再离开状态锁发出请求。
- SSE等待使用带谓词的条件等待，避免无数据变更的通知触发重复快照。

两项新增并发回报回归在修改前源码上均失败，在修复后通过。桥接离线回归共18项通过，亦在服务端执行通过。

23:05部署Python修复并仅终止卡死的两个桥子进程，由原后端监督器重新启动。随后十秒采样，新桥PID 2633367/2633369的CPU分别约1.5%/1.6%，三个桥均 `ready=true`、`healthy=true`、无同步错误。这是当前锁修复的线上验收证据，仍需较长时间观察复发情况。
