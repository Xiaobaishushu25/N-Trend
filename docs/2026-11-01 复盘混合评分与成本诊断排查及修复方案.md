# 复盘混合评分与成本诊断排查及修复方案

日期：2026-11-01。对象：截图中的 SM0 #7057、BU0 #7056、SH0 #7055，以及当前工作区的复盘实现。

后续状态：已按本方案实施3.0.4修复，见《2026-11-01 复盘数据链路与诊断修复》。下文保留排查时点的发现与修复前复现结果。

本次交付为排查、复现和修复方案，尚未修改产品代码、调用生产接口或执行历史重建。四个相关 Vue 文件在排查前已有未提交修改，本次按其当前内容检查并保留原改动。

## 1. 结论与证据边界

确定存在的主因是页面没有统一使用同一份已发布复盘结果：旧列表、新详情、旧详情兜底、两代百分制评分和原始五分制评分被多个组件分别取值。成本提示还通过“是否有两个价格”推断结算成功。

即使后台全量重放成功，这些前端取值与请求缺陷仍会发生。不能据此判断用户没有重放，也不能据此判断生产数据库混入了两批不同策略的信号。

直接加载当前 Vue 脚本、通过 Vue SSR 渲染当前抽屉模板，使用隔离构造数据复现了17项异常。复现中的7057等编号只是按截图命名的构造输入，并非已取得生产记录。

只读检查了六份本地数据库/快照：根目录 ntrend.db、data/ntrend.db、data-dev/ntrend.db、data/server_backup.sqlite 和两份 backups_temp 快照。它们均不含7055/7056/7057，也均未发现 review_current/review_results/review_jobs 表。这个结论只适用于这些本地副本，不代表生产库状态。

所以目前不能确认7057具体的 score_status、缺分解释、已发布版本及后台作业覆盖。需要在实际服务的数据上继续核对，不能把“缺历史”“跨换月”或“任务未完成”写成该信号的既定事实。

## 2. 实际数据链路

### 2.1 两种“重建”需要区分

1. `Services::rebuild_events`：按15分钟行情重新识别/补入原始预警、推进原始事件状态。原始入场分仍是五分制；当前函数自身没有执行清表，不能仅依据注释认定发生了清空全量重建。
2. `ReviewEngine::rebuild`：读取已有 `pattern_events`，用5分钟行情模拟固定一手首次1R退出，补充质量评分、过程证据、成本及诊断，写入 `review_results`、节点和持有记录，完成任务后事务发布 `review_current`。

第二种重建不会改写原始入场分，不重新识别另一批信号，也不会把五分制原始分替换成百分制。百分制质量评分是独立计算；当前固定1R复盘准入仍使用原始入场分≥2.5及计划风险≥10 tick。这个事实不等于所有用户所说的“新策略”都已采用该准入，需要用实际结果的 profile/parameter_hash 核对。

`completed` 表示任务完成并发布，不表示每条都有有效百分制评分或完整金额。评分失败、缺行情、缺日历、缺乘数有各自状态与 coverage。

主要代码：`crates/n-core/src/service/mod.rs:4406`；`crates/n-core/src/review/store.rs:106,182,255,487`；`crates/n-core/src/review/replay.rs:279`。

### 2.2 当前页面绕过了新发布结果

主列表实际路径：

```text
ReviewWorkbench → useReviewStore.loadReviewPage → api.getReviewPage
→ get_review_page → Services::review_page
→ pattern_events + 按当前15分钟行情只读补算评分
```

`Services::review_page` 没有读取 `review_current`。返回的是旧 `OutcomeDetail`，不含新结果的 `result_version`、`snapshot_id`、完整金额及诊断集合。

打开独立图表时，Workbench 又从 `row as any` 取 `result_version`，从 `review as any` 取 `currentSnapshotId`；当前类型和 store 都没有这些字段。编译器因 any 没有拦住。

图表先尝试新复盘查询；新查询正常返回空数组时，切换到旧列表。没有结果版本时，详情请求使用 `review-fixed-one-r-5m-v1`。但这只是 profile，真正 result_version 是 `事件ID-输入哈希`。服务端按事件ID和结果版本精确查找，因此这条默认路径查不到正常生成的结果。

新详情失败后，代码静默调用旧详情，人工拼出 `cost: {}`、`diagnostics: {}`、`multiplier: null`、空生命周期，继续作为新详情类型传入。

证据：`src/stores/review.ts:89`；`crates/n-core/src/service/review.rs:267`；`src/components/ReviewWorkbench.vue:405`；`src/views/ReviewChartView.vue:182,296`；`crates/n-core/src/review/store.rs:442,797`。

## 4. 为什么完整重放仍可能“没有分”

当前评分器会明确返回以下失败状态：S0前不足40根K线、缺S1/S2、缺预警K线、跨换月、交易时段缺15分钟K线、结构几何异常、ATR预热不足、过程证据不足等。它们与5分钟模拟能否开平仓是两个独立维度。

因此允许出现“复盘路径已处理、百分制无法评分”，也允许“评分可用、未发生模拟成交”。正确页面必须分别展示评分状态、模拟状态和成本覆盖，不能用一次completed或一个绿色提示概括三者。

对7057，必须读取真实返回的 `review_scores.status/explanations`、`quality.status/explanations`、`summary.coverage` 才能定位；本次没有取得该记录，不能指定其中某个失败原因。

## 5. 推荐修复顺序与接口设计

### 第一阶段：先停止误导性展示

在当前组件内修复评分回退、假结算、空值补零、状态误判；展开时加载详情，失败显示错误。补全选择级请求序号及身份校验。

这些是显示与请求修复，本身不需要删除信号或重新识别历史预警。完成后应能如实呈现“评分暂不可用”“详情未加载”“金额覆盖不足”等状态。

### 第二阶段：主列表与详情统一到已发布复盘

1. 主工作台的数据源改为 `reviewQuery`，分页改为 `reviewItems`；统计从同一snapshot的overview/groups读取，额外分类用aggregate。旧历史统计保留独立入口和明确标签，不作为新列表失败兜底。
2. 使用单独、强类型的新复盘store，存储请求、snapshot_id、revision、分页游标、匹配总数、每条result_version、任务状态和错误；原组件和旧store的any混合类型撤出新链路。
3. 给只有event_id的旧入口提供明确的“解析当前已发布结果”能力。建议独立查询接口，返回当前版本；随后仍按真实版本读详情。不使用profile替代，也不从另一条信号继承currentVersion。
4. 新结果为空时显示“尚无已发布结果/正在计算/计算失败/筛选无匹配”的实际状态；通过metadata/jobs区分，不自动读取旧事件顶上。
5. 详情、图表与导航都绑定 `(event_id,result_version)`；与列表身份不匹配的响应直接丢弃。

注意：不能只把 getReviewPage 换成 reviewQuery。现有 `ReviewSummary` 没有卡片正在使用的entry/stop/target/rr、完整空间/关键位分项；直接替换会导致价格和空间显示为空，或诱发逐行请求详情。

建议在新摘要协议中补充当前卡片真正需要的冻结字段：计划入场、初始止损、原始参考目标、计划风险、到S1空间R，及必要的空间/关键位评分与评分原因摘要。模拟固定1R目标必须单独命名，不与原目标混用。摘要只存小字段，过程证据和逐K记录仍留在详情，避免列表N+1详情请求。

### 第三阶段：统一面板数据模型与成本表达

- 抽屉只接收新复盘摘要和同版本详情。先校验身份，再确定唯一summary。原始形态事实读original_event，模拟执行事实读新结果/节点。
- 将 cost 从 `Record<string,unknown>` 改为与服务端一致的类型，保留现有字段含义。状态显示区分未成交、持有中、R已结算但金额不可计价、估算金额已结算、覆盖不足。
- 显示“模拟/估算成本”和实际cost_version、tick、乘数、滑点、附加费用。现有模型开平各1 tick已计入成交价，净额仅额外扣0.5 tick；不得重新扣一次2.5 tick。
- `cost.settled=true`只说明路径closed，不能单独证明金额覆盖；必须结合multiplier、金额及coverage判断。零手续费或零净收益如果合法，应用空值判断而非真假值判断。
- 诊断用中文标签、明确时间口径；保留不可用原因。修正b/a速度的根数分母及5m/15m计数，尊重MFE/MAE的精度与上下界。

### 第四阶段：生产数据核验后决定是否补算

先以只读方式检查：

1. 实际客户端/服务端版本以及正在访问的服务；三个事件对应的原始信号与当前已发布结果。
2. 最近重建job的status、范围、完成品种、processed_signals、revision、coverage和errors。
3. `pattern_events`到`review_current`的缺失覆盖；三个事件是否有review_results却未发布；当前head是否指向期望profile与参数版本。
4. 详情的真实评分失败原因、成本字段和乘数；列表携带的结果版本与详情是否完全一致。

如果结果完整，只修页面即可。如果只有缺失/失败品种才补算相应复盘结果；输入行情/日历不足时先解决具体缺口。若新增摘要字段需要重新生成发布摘要，仅重建复盘产物，保留原始事件和ID。不能先清空所有信号重扫来掩盖前端缺陷。

服务端和客户端的协议变更须同步发布，遵循项目现有严格版本校验。重建过程继续使用既有staging与事务发布，避免半批结果暴露。

## 6. 验收标准

1. 同一主评分列始终为用户选择的指标。缺v2时显示原因，不用v1或2.7/5替代；显式选择旧入场分时才显示五分制。
2. 从筛选后的任意页打开图表，品种、筛选、排序、分页位置、snapshot和结果版本保持一致；列表为空、快照过期和服务重启有明确处理。
3. 直接展开未选中的7057会发起对应详情请求；无详情或失败时不出现结算成功，面板不会显示其他信号的内容。
4. 快速执行7057→7056→7055并让网络响应逆序，最终图表、抽屉、价格、评分和状态都属于7055；旧请求不能提前结束新loading。
5. 完整详情含100/90元及诊断而列表摘要缺字段时，显示完整详情值；没有乘数时明确提示金额不可计价，R值按实际覆盖展示。
6. pending/missing_data/missing_calendar/missing_parameters/ambiguous不能被显示为已结算。只有profile明确支持的target_1r显示固定1R。
7. 未成交不显示成交价；计划价与成交价分别保留；追价、跳空、滑点分别展示；未知滑点不显示零。
8. 5分钟持有记录条数与15分钟持仓根数区分；未知MFE/MAE不补零，有界值显示区间。
9. “全量重放完成”至少可追溯job、revision、品种覆盖和失败分布；不把无分记录静默隐藏，统计分母与列表同一快照。
