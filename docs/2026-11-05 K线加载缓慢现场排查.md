# K线加载缓慢现场排查（2026-11-05）

## 结论

本次交易时段卡顿的主要证据指向交易执行热路径占用 Tokio 工作线程：逐笔行情观察反复深拷贝全部条件单及其 JSON 证据，策略分发进一步复制完整执行状态。K线请求的数据库异步读取与其他任务一起被延迟调度。只增加图表缓存、SQL索引或连接数不能消除这项开销。

这是现场采样与代码核对支持的主因判断，尚未通过修改前后干预实验量化修复收益。排查没有修改生产源码、数据库、配置或执行模式，没有重启服务，也没有提交交易操作。服务端仅生成了两个短时 perf 诊断文件。

两条执行计划均使用 `sqlite_autoindex_klines_1`，匹配symbol、timeframe及时间范围。独立连接与SQLx并非同一实现，不能据此精确拆分SQLx各阶段，但足以反驳“此查询固有执行成本就是数秒”。

13:43现场 `top -H` 显示两个 Tokio 工作线程分别占87%和72% CPU，SQLite线程几乎空闲。`vmstat`后两个样本CPU空闲约1%，没有换入换出。可用内存约750MiB，已有swap占用约440MiB；没有本窗口持续换页的证据。不能把累计swap占用直接当作此次故障原因。

## CPU调用栈与代码位置

先做8秒49Hz普通采样，再做5秒19Hz DWARF调用栈采样。后者147个样本、无丢样，约65.99%的包含子调用样本经过 `ExecutionEngine::observe_quotes`，52.38%经过 `on_quote_batch`，18.37%经过策略 `dispatch`。这些比例有调用包含关系，不能相加。

大量样本位于 `ConditionOrder::clone`、JSON BTreeMap/String复制、malloc/free及JSON析构。具体对应：

1. `crates/n-core/src/trader/execution.rs` 的 `on_quote_batch()` 对批中每一笔事件逐个调用 `observe_quotes()`。
2. `observe_quotes()` 在每次观察时执行 `s.conditions.values().cloned().collect::<Vec<_>>()`，排序后再判断，深拷贝成本随全部历史条件单增长。条件单携带冻结策略计划及证据，不只是少数价格字段。
3. `crates/n-core/src/trader/strategy_runtime.rs` 的 `dispatch()` 对接收该事件的策略执行 `guard.clone()`，再复制该版本的条件单、订单和策略JSON状态，并复制策略旧状态供比较。
4. `reconcile()` 也复制完整执行状态，但本次采样的最大调用归属是盘口观察，不将柜台恢复误写为唯一主因。

生产持久化状态的只读体积统计：默认实例有561条条件单（序列化约2.28MB）、4683条执行委托（约3.15MB），整个状态文件约5.94MB。另一个策略实例有68条条件单（约0.66MB）、策略状态约0.60MB。体积按文件内容/JSON重新序列化统计，不等于精确内存占用。

因此，即使当天没有新增大量活跃任务，历史档案与证据累积仍会增加每笔观察的复制与释放成本。这解释了为什么以前降低查库量后，问题仍可能随运行和历史积累再次显现；不代表已经证明所有时段的延迟都只有这一个原因。

## 修复方向及验收要求

优先减少逐笔路径的复制成本：让盘口观察读取轻量观察数据，共享不可变策略定义/计划/证据，避免把历史条件单和委托档案整体复制到每笔工作快照。策略事务快照需要保留失败回滚语义，采用按需或写时复制；不能直接原地修改以换取速度。

需要保持逐笔行情顺序、入场/退出判断、持仓保护、柜台成交恢复和“关键状态持久化后才报单”的既有语义。不能通过丢行情、清历史、停用实例或跳过风控来降低CPU。同步计算与持久化的线程隔离可作为后续防护，但应先减少总工作量，避免仅将CPU争用转移到其他线程。

修复验证至少包括：

- 用包含数百条件单、数千历史委托、较大JSON证据的冻结状态测逐笔处理分配量和耗时，对照小状态，防止只用空实例验收。
- 对相同行情序列核对条件单、委托意图、成交恢复及风控状态与原实现一致，覆盖失败回滚。
- 交易时段跨多个刷新及柜台同步周期同时测K线P50/P95/最大值、Tokio调度延迟、HTTP响应头/正文、CPU、执行行情队列与缺口增量。
- 本次13:45:13同一SR0请求已自然回落到295ms（服务端172ms），说明延迟存在波动，单次快速请求不能视为修复成功。
